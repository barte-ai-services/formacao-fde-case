Formação FDE · caso Já Chegou

Arquitetura de referência.
O agente propõe, uma pessoa aprova.

Uma proposta de stack para o grupo partir, com Python no backend e Astro com React no front. O agente roda no Claude Code e lê o caso por um servidor FastMCP. Quem aprova entra numa tela em Astro, e tudo grava no Supabase com o login de quem pediu. É o banco que decide quem pode o quê.

O agente propõe.Ele lê notas, ordens e recebimentos e grava uma proposta. Não tem permissão para aprovar nada.
Uma pessoa aprova.Ela precisa estar logada e ter o papel da alçada daquele valor. A decisão leva o nome dela.
O banco recusa o resto.As regras ficam no banco do Supabase, com RLS. Um front com bug ou uma tool mal escrita não passa por cima delas.

As camadas

Quatro faixas: quem usa, o que roda na borda, onde ficam os dados e onde fica o código. As setas cheias são chamadas, e a tracejada é o banco avisando o backend.

Arraste o diagrama para o lado para ver tudo.

Uma aprovação, passo a passo

O caminho de uma nota, da chegada até a auditoria. A ordem é a real: cada passo depende do anterior.

  1. A nota chega.O XML e o PDF vão para um bucket privado do Storage, e a nota vira uma linha em notas com o caminho dos arquivos.Storage · notas
  2. O lote acorda o agente.Um workflow agendado nas Actions roda o Claude Code com as skills do caso. Ele entra no MCP como o usuário do agente, que tem o papel agente.GitHub Actions · Claude Code
  3. O agente lê e propõe.As tools do FastMCP leem a nota, a ordem de compra e o recebimento da doca com o token do agente. O resultado é uma linha em propostas, com a justificativa. A alçada não vem do agente: o banco a calcula pelo valor da nota.FastMCP · RLS: o agente só insere em propostas
  4. O banco avisa quem decide.Um webhook do banco chama o /api a cada proposta nova. O FastAPI chama a função quem_avisar, que devolve só os e-mails de quem tem o papel daquela alçada, e manda o aviso pelo Resend com o link da tela.Webhook · FastAPI · Resend
  5. Uma pessoa decide.Ela entra no Astro com o login do Supabase e vê a nota ao lado da ordem e do recebimento. Ao aprovar ou recusar, o front chama o /api com o JWT dela.Astro com React · FastAPI
  6. O banco confere e registra.A policy compara o papel do JWT com a alçada que o banco tirou do valor da nota e recusa o que não bate. Se passar, um trigger grava em auditoria quem decidiu, quando e o quê.Banco Supabase · RLS · trigger de auditoria

De hora em hora, o Cron do Python Worker procura propostas paradas há mais de dois dias e manda um lembrete. As faixas de alçada vêm do caso (R$ 5 mil, R$ 20 mil, R$ 100 mil e acima). Os papéis de cada faixa aqui são exemplo: quem decide cada uma é pergunta para o cliente.

Front-end · Astro com React

A tela de quem aprova

  • O Astro monta as páginas no servidor, com a sessão do Supabase guardada em cookie.
  • As partes interativas são ilhas React: a fila de propostas, o comparativo da nota e os botões de aprovar e recusar.
  • Ele também hospeda a tela de consentimento do OAuth, aquela em que a pessoa autoriza o Claude Code a usar o MCP em nome dela.
  • O front não fala com o banco para decidir: ele chama o /api com o JWT da pessoa.

npm create astro@latest ja-chegou-web
cd ja-chegou-web
npx astro add react cloudflare
npm install @supabase/supabase-js @supabase/ssr

# publicar num Worker
npm run build
wrangler deploy

Login e papéis

  • O login é o Supabase Auth, por e-mail ou SSO.
  • Um Custom Access Token Hook põe o papel da pessoa (analista, coordenacao, diretoria ou agente) dentro do JWT.
  • O mesmo JWT chega ao /api e ao /mcp, e o banco lê o papel com auth.jwt().
-- o hook que põe o papel no token
create or replace function public.custom_access_token_hook(event jsonb)
returns jsonb language sql stable as $$
  select jsonb_set(event, '{claims,papel}', coalesce(
    (select to_jsonb(p.papel) from public.pessoas p
      where p.id = (event->>'user_id')::uuid),
    'null'::jsonb));
$$;

-- só o Auth executa o hook e lê os papéis
grant usage on schema public to supabase_auth_admin;
grant execute on function public.custom_access_token_hook
  to supabase_auth_admin;
revoke execute on function public.custom_access_token_hook
  from authenticated, anon, public;
grant select on public.pessoas to supabase_auth_admin;
create policy "o hook lê os papéis" on public.pessoas
  for select to supabase_auth_admin using (true);

# supabase/config.toml (na nuvem: Authentication › Hooks)
# [auth.hook.custom_access_token]
# enabled = true
# uri = "pg-functions://postgres/public/custom_access_token_hook"

Backend · Python

FastMCP no FastMCP Gateway

  • As tools do caso: listar as notas pendentes, ler a nota, a ordem e o recebimento, e registrar a proposta.
  • O SupabaseProvider troca o token Bearer fixo por OAuth 2.1, com o Supabase como servidor de login. Ative o OAuth Server e o registro dinâmico de clientes no projeto. O projeto precisa assinar o JWT com chave assimétrica: o padrão do SupabaseProvider é ES256, e com RSA você passa algorithm="RS256".
  • Cada tool pega o token de quem chamou (get_access_token().token) e o repassa ao Supabase. Assim, o RLS vale também para o agente.
  • Ele é publicado no FastMCP Gateway, da Prefect: você conecta o fork, aponta main.py:mcp e a URL sai em *.fastmcp.app/mcp.
# main.py · uv add fastmcp
from fastmcp import FastMCP
from fastmcp.server.auth.providers.supabase import SupabaseProvider
from fastmcp.server.dependencies import get_access_token

auth = SupabaseProvider(
    project_url="https://<ref>.supabase.co",
    base_url="https://ja-chegou.fastmcp.app",
)
mcp = FastMCP("ja-chegou", auth=auth)

@mcp.tool
async def ler_nota(chave: str) -> dict:
    """Lê uma nota pela chave de acesso."""
    jwt = get_access_token().token  # o RLS vale
    ...

# local: fastmcp run main.py:mcp --transport http --port 8000

FastAPI num Python Worker

  • O /api do front: listar as propostas, gerar a URL assinada do PDF e registrar a decisão.
  • Cada chamada repassa ao Supabase o JWT de quem está logado. O backend não usa a chave secreta para decidir nada.
  • A rota /api/avisos recebe o webhook do banco, confere o segredo compartilhado e manda o e-mail pelo Resend.
  • O mesmo Worker tem um Cron Trigger para os lembretes.
  • O aviso e o Cron são os únicos que rodam sem uma pessoa logada. Eles usam a chave secreta só para chamar duas funções do banco, quem_avisar e propostas_paradas, que devolvem e-mails e links e nada mais. As duas são security definer, com o execute revogado de public, anon e authenticated e dado só ao service_role.
# criar e rodar
uvx --from workers-py pywrangler init
uv add fastapi
uv run pywrangler dev
uv run pywrangler deploy

Dados · Supabase

O banco no Supabase: RLS, Storage e o webhook

  • O esquema vive em migrações versionadas no fork, e o desenvolvimento usa o Supabase local com Docker.
  • Todas as tabelas têm RLS ligado. O agente insere em propostas e não toca em aprovacoes. Uma pessoa só aprova até o limite do papel dela, e a alçada sai do valor da nota, nunca do texto do agente.
  • O webhook é um trigger com pg_net. A URL e o segredo dele ficam no Vault, fora das migrações.
  • O bucket notas é privado, e o PDF só abre por URL assinada.
# local e nuvem
supabase init
supabase start
supabase migration new esquema_inicial
supabase link
supabase db push --remote

Fork, Actions e o lote do agente

  • Um fork com três pastas: web/ (Astro), api/ (FastAPI) e mcp/ (FastMCP), mais supabase/ com as migrações.
  • Depois do merge na main, as Actions publicam os dois Workers e aplicam as migrações. O FastMCP Gateway publica sozinho a partir do fork.
  • O lote é um workflow com schedule que roda o Claude Code com o token do claude setup-token.

O banco, no Supabase

O banco é o Postgres do próprio Supabase, sem outro banco ao lado. São oito tabelas e um bucket. A última coluna mostra quem pode escrever em cada uma, e quem impõe isso é o RLS.

TabelaO que guardaQuem escreve
pessoasO papel de cada usuário do Auth, que o hook põe no JWT. O e-mail vem de auth.usersSó a diretoria
fornecedoresCNPJ, razão social e dados de pagamentoCadastro, pela importação
notasChave de acesso, emitente, valor, itens e o caminho do XML e do PDF no StorageA importação das notas
ordensOrdens de compra: itens, quantidades e preços combinadosA importação do ERP
recebimentosO que a doca conferiu de cada ordemA importação da doca
propostasO que o agente sugere para cada nota, com a justificativa. A alçada é calculada por um trigger a partir de notas.valor, e o agente não consegue mudá-laSó o papel agente
aprovacoesA decisão de uma pessoa sobre uma proposta: aprovar ou recusar, e o motivoSó uma pessoa com o papel da alçada
auditoriaCada mudança: quem, quando, a tabela e o antes e o depoisSó os triggers; ninguém altera nem apaga
bucket notasXML e PDF originais, num bucket privadoA importação. A leitura é só por URL assinada

Quem se autentica onde

Em uso, só o aviso (o webhook e o Cron) lê fora do RLS, e só o que precisa para avisar: os e-mails e os links. Os passos de publicação têm acesso amplo, e as credenciais deles ficam nos secrets do repositório.
